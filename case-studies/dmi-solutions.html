Unifying Two ERPs Under One GL

The Trademark Cosmetics → DMI Solutions case study.

Engagement Overview

The client began as Trademark Cosmetics, a manufacturer and distributor operating on the Epicor ERP platform. Partway through the relationship, Trademark combined with a second operating company running on the Alere ERP system. The combined entity was rebranded DMI Solutions, and the analytics engagement carried forward across the name change — meaning the data platform had to be built to serve two legacy ERP environments as if they were one company, while the corporate identity above them changed underneath it.

The full technical stack — the Azure VM, the TimeXtender (TDI) instance, the ingestion pipelines, and the Power BI reporting layer — was built and deployed entirely in Azure, giving both legacy companies a single cloud-hosted analytics environment regardless of which ERP their transactions originated in.

The Challenge

Two companies, two ERPs, one set of financials to report on. Epicor and Alere each carried their own chart of accounts, and neither had been designed with the other in mind. Before any dashboard or financial report could be trusted, the platform had to answer a basic question: when a GL transaction posts in Alere, what account does it correspond to in the model everyone downstream will actually use?

Beyond the chart-of-accounts mismatch, the two systems delivered data through completely different mechanisms — Epicor via a live API connection, Alere via CSV extracts dropped into SharePoint on a daily cadence. Any unified GL structure had to absorb both delivery patterns without one source's quirks (a delayed file drop, a late-posted transaction) silently corrupting the numbers for the other.

The Solution: GL Account Consolidation

Rather than build a brand-new, neutral chart of accounts, the team made the Trademark/Epicor structure the model of record. New accounts were created in that model wherever Alere's chart didn't already have an equivalent, and a persistent Alere-to-Trademark account mapping table was built to translate every Alere GL transaction into its corresponding Epicor-model account. That mapping isn't a one-time crosswalk — it's a living reference table, appended to whenever Alere posts activity against a new account that hasn't been mapped yet, so the model stays current as the underlying business keeps operating.

Because both ERPs delivered GL data at the same transaction-level grain, the mapping didn't need to reconcile summarized entries against detailed ones — it only had to translate account identity, not transaction granularity. That made the crosswalk itself the whole solution to the chart-of-accounts problem, rather than one piece of a larger grain-reconciliation exercise.

The Solution: Incremental Loading Across Two Delivery Mechanisms

Epicor data was pulled repeatedly through its API on an incremental basis. Alere's daily SharePoint file drops were picked up the same way — the CSVs land, and the load process picks them up seamlessly without manual intervention. But file-based delivery introduced a timing problem live API polling didn't have as severely: transactions don't always arrive in the system on the day they actually happened.

To solve for that, every incremental record carries two dates: a post date (when the transaction actually occurred in the business) and a create date (when the record actually landed in the source system — which, for file-based Alere data, can trail well behind the post date). Both dates are fully built into the incremental load logic, so the platform can correctly place a transaction in the period it belongs to, even when it's picked up late, rather than either missing it or misattributing it to the day it happened to arrive.

Mapping to the AAIM Method

Acquire

Two structurally different ERPs, two delivery mechanisms — a live Epicor API and daily Alere file drops into SharePoint — were both brought into one Azure-hosted TimeXtender environment. Acquisition here wasn't just “get a connection”; it meant designing ingestion that could tolerate the very different reliability and timing characteristics of an API versus a file drop, and land both in a state ready for the same downstream model.

Automate

The account-mapping table and the post-date/create-date incremental load logic are what turned that acquisition into something that runs on its own. New Alere accounts get mapped as they appear rather than requiring a manual quarterly review, and late-arriving file data is placed in the correct period automatically rather than triggering a manual correction. That's the automation layer doing the reconciliation work a human would otherwise have to redo every reporting cycle.

Outcome

The engagement didn't end with the initial buildout. It continued through a validation and support phase, then carried through the Trademark-to-DMI Solutions rebrand, and into a later phase that extended the same Alere and Epicor pipelines to cover additional inventory and reconciliation work. The GL account model built during the original consolidation has remained the backbone that later phases of the engagement built on top of — a sign that the Acquire and Automate work held up as the business itself changed shape.
